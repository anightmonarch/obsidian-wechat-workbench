# 图片宽度保真设计:预览画布对齐微信正文宽度 + 窄图上采样

日期:2026-11-08
状态:已批准(修复用户报告的「手机截图在公众号里两侧留白,Obsidian 预览却看不出来」)

## 问题(实测证据)

用户报告:手机截图图片发布到公众号后,桌面端阅读页两侧出现明显空白;插件预览中却看不到。

在真实公众号环境实测(Commit日记 测试草稿 + 已发表文章 `mp.weixin.qq.com/s/-I8IkAUgQ8q0dxZyILkBHg`):

1. 微信桌面端阅读页正文固定宽度 **677px**(`.rich_media_content`),编辑器画布约 578px。
2. 微信按上传图片的自然宽度渲染:宽度 ≥677 的图被 `width: 677px !important` 拉满;
   自然宽度 588px 的手机截图被固定为 `width: 588px !important` 并水平居中,两侧各留 ~44px 空白。
3. 垂直间距无异常:全文所有相邻块间隙 ≤24px(figure margin 1.5em 与 p margin 正常折叠)。
4. 插件预览画布宽度跟随面板(~567px),比 588px 的图更窄,`max-width: 100%`
   把图缩放铺满 —— 预览与微信实际渲染不一致,违反「可验证预览」不变量。

根因不是垂直间距,而是:**窄于 677px 的图片在微信里必然居中留白,而预览画布过窄把这一现象掩盖了**。

## 目标

- 预览忠实反映微信桌面端阅读页的横向布局(包括窄图两侧留白)。
- 接近正文宽度的静态图自动上采样,发布后铺满正文宽度,与预览观感一致。

## 非目标

- 不放大「故意小尺寸」的图(表情、二维码等):低于下限(480px)的图保持原样。
- 不处理 GIF(动画帧会丢失;GIF 现有路径本就不重编码)。
- 不引入 preflight 警告:上采样已覆盖 480–677px 区间,更窄的图视为有意小图。
- 不改变 canonical HTML 结构与内容哈希(预览画布是宿主 UI,不是产物)。

## 方案

### 1. 剪贴板/上传归一化:窄静态图上采样

`normalizeImageBytesForClipboard`(src/media/electron-image-normalize.ts)新增规则:

- 常量 `WECHAT_BODY_WIDTH = 677`、`WECHAT_BODY_UPSCALE_MIN_WIDTH = 480`。
- 条件:MIME 为 jpeg/png/webp(静态图,GIF 除外),且 `480 ≤ width < 677`。
- 动作:等比放大到 `width = 677`(拉伸比 ≤ 1.41×,截图与照片肉眼无损)。
- 放大后走既有 JPEG 重编码与 3 MiB 质量循环;mediaCache 以归一化后字节哈希,无需改键。
- 与既有「超过 2560px 缩小」规则对称:一收一放,均无设置项。

### 2. 预览画布固定 677px

- `ArticlePreviewRenderer.render` 在 `.wechat-article` 外包一层
  `.wechat-workbench__preview-canvas`(固定宽 677px,水平居中)。
- 面板窄于 677px 时用 ResizeObserver 设 `canvas.style.zoom = min(1, 可用宽/677)`,
  等比缩放整个画布,保持横向比例真实(窄图的留白按比例可见),不产生横向滚动。
  Chromium `zoom` 影响布局,无需补偿高度;非 Chromium 环境特性检测后跳过。
- 画布仅存在于预览 UI;canonical HTML、剪贴板与草稿内容不变。

## 验收

- 单测:上采样触发/不触发边界(479/480/676/677/GIF/空图);预览画布存在且宽 677。
- 端到端:重建后的插件在测试 Vault 走「复制 → 公众号编辑器粘贴」,窄图 data-w=677 铺满;
  预览中同一文章在 677 画布上呈现与微信一致的比例。
- 回归:现有全量测试、typecheck、lint 通过。

## 后续(另行立项)

- 用户指南补充「想让图片铺满桌面端正文,请使用 ≥677px 宽的图」。
